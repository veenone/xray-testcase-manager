## Feature A — Cross-project execution members + bugs + traceability

The whole "members live in another project" story, in one feature: the execution
shows its foreign-project member tests (A1), bugs linked to those foreign members
appear in the bug list (A2), and the execution traceability Sankey can include
cross-project members (A3).

### A1 — Member tests

**Problem.** `GetContainerBoard` (`internal/testrepo/testrepo.go:~1175`) INNER JOINs
`test_container_test` to `test_case`, and the test pull only fetches the profile's
own project (`SearchTestsPage` JQL `project = <key>`). So a member test from
another project has a membership row but no `test_case` row, and the join drops
it — the execution shows no members.

**Design.**
- **Schema v24:** new table `external_test (profile_id, jira_key, summary, status,
  project_key, PRIMARY KEY (profile_id, jira_key))` — a minimal cache for tests
  referenced by container memberships but outside the profile's project, kept
  separate from `test_case` so they never appear in the Browse grid. Additive
  migration; bump `schemaVersion` to 24.
- **Jira client:** `ListTestsBasic(ctx, keys []string) ([]TestBasic, error)` —
  chunked `key in (…)` search (`fields=summary,status,project`), returning
  `{Key, Summary, Status, ProjectKey}`. Real path; demo returns seeded entries.
  Marked `TODO(xtm)` for live verification like the other `internal/jira` calls.
- **Sync:** in `syncContainers` (`internal/syncer/engine.go`), after
  `ReplaceAllContainerLinks`, collect member `test_key`s **absent from
  `test_case`** (a new `repo.ContainerMemberKeysMissingTests(profileID)` query),
  call `ListTestsBasic`, and `ReplaceExternalTests(profileID, …)`. Best-effort: a
  fetch failure logs and is swallowed (members still show by key).
- **Board:** `GetContainerBoard`'s member query switches to a LEFT JOIN and
  coalesces from `test_case` then `external_test`:

  ```sql
  SELECT l.test_key,
         COALESCE(t.summary, x.summary, '')  AS summary,
         COALESCE(t.status,  x.status,  '')  AS status,
         (t.jira_key IS NULL)                AS is_external,
         l.run_status
  FROM test_container_test l
  LEFT JOIN test_case     t ON t.profile_id = l.profile_id AND t.jira_key = l.test_key
  LEFT JOIN external_test x ON x.profile_id = l.profile_id AND x.jira_key = l.test_key
  WHERE l.profile_id = ? AND l.container_key = ?
  ORDER BY l.test_key
  ```

  Every membership now yields a row. `TestPlanBoardRow` gains `isExternal bool`
  (json `isExternal`); the board renders a small **ext** badge (and the foreign
  project is visible in the key). Run-result editing is unchanged (it targets the
  exec+test membership, project-agnostic).
- **Demo:** seed a DEMO execution whose members are `XRAYINT-*` tests, plus the
  matching `external_test` rows, so the feature is exercisable offline.

### A2 — Cross-project bugs

**Problem.** Reported case: active project A, sub-task execution in A, the bug in A,
but the member **test** lives in project B. The bug never appears in the
execution's bug list. Two causes:
1. `syncBugs` (`internal/syncer/engine.go:~365`) harvests bug links by walking
   `AllTestKeys(profileID)` (`testrepo.go:~2087`), which reads only `test_case` —
   so a bug reached *through* a project-B member test is never collected.
2. `ListTestsForBug` (`internal/testrepo/bugs.go:~156`) and the container's
   related-bug query INNER JOIN `test_case`, dropping any project-B member test.

**Design.**
- **Harvest from member tests too.** Extend the cross-project fetch from A1:
  `ListTestsBasic` also returns each test's `issuelinks` (the same payload the
  Test sync already reads), so `syncContainers` can harvest bug links from the
  external member tests. After caching `external_test`, walk those tests'
  links, keep those whose target issuetype matches the profile's configured bug
  issue type, upsert the bugs into `bug` and the links into `test_bug`
  (`ReplaceAllBugs` / `ReplaceAllBugLinks` already accept cross-project
  `project_key`). Best-effort; a fetch failure logs and is swallowed.
- **Surface them.** Add a **related-bugs list** to the execution/container detail
  in `ContainersView.tsx` (a new `repo.ListBugsForContainer(profileID, containerKey)`
  that joins `test_container_test` → `test_bug` → `bug`, LEFT JOIN `test_case`
  **and** `external_test` for the test summary, so project-B members are not
  dropped). `ListTestsForBug` likewise switches to LEFT JOIN `test_case` +
  `external_test` with COALESCE, so the Bugs panel's per-bug test list shows the
  foreign member by key/summary.
- **Demo:** seed a bug in the profile project linked to an `XRAYINT-*` member of
  the seeded cross-project execution, so the related-bug list is non-empty offline.

### A3 — Cross-project execution traceability

**Design.** With A1's `external_test` cache in place, the execution traceability
Sankey (`GetSubTaskTraceability` / the execution tab) can include cross-project
members by coalescing the test label from `test_case` then `external_test` (same
LEFT JOIN as the board) instead of dropping them. A **"Include cross-project
members"** toggle on the execution/sub-task traceability tab controls whether
those members are drawn (default on); it threads to the Sankey producer as a
`crossProject bool` (the same flag already in `ExportTraceability`, Feature B).
A short inline help line under the tab explains it:

> *Cross-project members.* When a Test Execution includes tests from another Jira
> project, enable this to show those tests in the flow. They are fetched into a
> local cache during sync; if a member is missing, run a sync first.

## Feature B — Traceability XLSX export (active tab)

**Design.** An **Export…** button on the Traceability view exports the **active
tab** (Requirement / Execution / Sub-task) to a `.xlsx`, respecting that tab's
current filters, via a new binding following the existing SaveFileDialog +
`os.WriteFile` pattern (`ExportRequirementAudit` is the model, `app.go:~2117`):

```go
func (a *App) ExportTraceability(profileID, kind string,
    planFilters, execFilters []string, crossProject bool,
    reqFilters, parentFilters []string) (string, error)
```

`kind` ∈ `"requirement" | "execution" | "subtask"`. The workbook has two sheets
(`writeXLSX` gains a multi-sheet helper `writeXLSXSheets(sheets []namedRows)`;
the existing single-sheet callers are untouched):

- **Flow** — the Sankey edge list with resolved labels: `Source`, `Target`,
  `Value` — the "Sankey format", ready to drive a Sankey in Excel / Power BI.
  Built from the relevant Sankey producer's `Links` (labels looked up from
  `Nodes`).
- **Table** — flat per-thread rows for that diagram, with the active filters:
  - execution → `Test Plan`, `Test Execution`, `Test`, `Run status`
  - requirement → `Requirement`, `Coverage`, `Test plan`, `Test`, `Run result`
  - subtask → `Parent`, `Test Execution`, `Test`, `Run status`

  Each kind gets a small flat-rows query in `internal/testrepo` (sibling to its
  Sankey producer, sharing the same WHERE/filters). The execution and subtask
  rows come from `test_container_test`; the requirement rows reuse
  `ListTestsForRequirement` per filtered requirement.

Frontend: the active tab passes its `kind` + its current filter state to
`ExportTraceability`; a success notice shows the saved path (as `exportAudit`
does in `RequirementsView`).

## Feature C — Create a Test Execution from selected bugs

**Design.** The Bugs panel (`BugsPanel.tsx`) gains a **checkbox per row** and a
**Create Test Execution** action, enabled when ≥1 bug is checked. On click it:
- collects the de-duplicated **union of the checked bugs' linked test keys** —
  already present on the loaded `BugWithTests.testKeys`, so no extra fetch;
- prompts for a name (default `Verify bugs: <KEY, KEY…>`, truncated) via the
  existing `usePrompt`;
- calls `CreateContainerAndAllocate(profileID, "testexec", name, testKeys)` (the
  local-first create+allocate already in `testrepo`, `app.go:~1847`), which makes
  a pending execution with a temp key, committed to Jira like any container;
- shows a notice with the temp key + member count and bumps `refreshKey`.

If a checked bug has no linked tests it contributes nothing; if the union is
empty the action is disabled with a hint. (Bug-linked tests are profile tests, so
no cross-project member concern here.)

## Feature D — Fix truncated detail picker dropdown

**Problem.** The `+ Add precondition` / `+ Link requirement` pickers render
`SearchableSelect` whose `.multiselect-panel` is `position: absolute; right: 0`
(`App.css:~941`). Inside the detail panel (`.detail { overflow: hidden }`,
440 px), a right-anchored panel opens leftward and is clipped at the detail's
left border.

**Design.** Scope a CSS override to the detail-context pickers (they already carry
`className` `pre-add` / a requirement equivalent — add `req-add` if missing):

```css
.pre-add .multiselect-panel,
.req-add .multiselect-panel {
  left: 0;
  right: auto;
  max-width: 100%;
}
```

so the panel opens within the detail's width instead of off its left edge. This
also covers the multi-pick from Feature E (same panel class). No JS change.

## Feature E — Bulk add requirements / preconditions per test

**Design.** Replace the single-pick `SearchableSelect` for `+ Add precondition`
and `+ Link requirement` in `TestDetail.tsx` with a **multi-pick** picker: a
searchable checkbox list plus an **Add N** button that links all ticked entries
in one apply. The backend already replaces the whole set
(`applyPreconditions` → `SetTestPreconditions`, `applyRequirements` →
`SetTestRequirements`, both array-based), so the handler passes the union
(current keys + ticked) in a single call. Reuse/extend the existing `MultiSelect`
look (search box + checkboxes) with a confirm action; the `__new__`
"create new precondition" option remains available as a separate control.

## Feature F — Duplicates: compare summaries

**Problem.** Duplicate groups already cluster by *normalized* summary
(`duplicates.go:~174`), so members can have differing raw summaries (case,
whitespace, punctuation); only **Compare steps** exists.

**Design.** Add a **Compare summaries** action beside **Compare steps** on each
group. It opens a side-by-side modal (same shape as `StepCompareModal`) showing
each member's **raw summary** (and description), with differing fields
highlighted, plus the group's normalized summary for reference. The data is
already on the group's `DuplicateMember`s (summary) plus a cheap
`GetTest`/cached description per member; no new grouping logic. Frontend-only
beyond a possible `description` field on the member.

## Feature G — Duplicates: scan-steps progress

**Problem.** The summary scan (`ScanDuplicates`) is instant SQL, but computing
**step verdicts** fetches steps per group (`ScanDuplicateGroupSteps`) and is done
one group at a time with no progress.

**Design.** Add a **Scan steps** action (a new `ScanAllDuplicateSteps(profileID)`
binding) that walks every group with an `unscanned` verdict, fetches its members'
steps, records fingerprints, and emits progress events — reusing the
`sync:progress` event channel with a stage label (e.g. `Scanning duplicate steps`)
and `Fetched/Total` = groups done/total. The Duplicates view shows a progress
bar + status in its toolbar (the `SyncBar`-style readout). The plain **Scan**
(summary regroup) keeps a brief busy state. Best-effort per group: a failure
logs and continues.

## Feature H — Test Calls: progress + toolbar + verified sync

**Design.**
- **Toolbar parity.** Re-style `TestCallsView`'s header to match `DuplicatesView`:
  a `dup-toolbar`-style row (the **Sync** button + a last-synced note + a spacer),
  with the existing call counts moved into a `dup-tiles`-style summary-tile row
  beneath it. Reuse the Duplicates CSS classes so the two views read the same.
- **Progress.** Route `SyncTestCalls` through the partial-sync progress path so it
  emits `sync:progress` per caller (stage `Refreshing test calls`,
  `Fetched/Total` = callers done/total). This means refactoring the bespoke
  `App.SyncTestCalls` loop (`app.go:~555`) to emit events via the same
  `runtime.EventsEmit(a.ctx, "sync:progress", …)` mechanism, with a terminal
  done; the status bar then reflects it like the other per-view syncs.
- **Verify the sync.** Confirm end-to-end on demo that `SyncTestCalls` actually
  refreshes the call graph (it re-pulls `DistinctTestCallers` steps via
  `GetTestSteps` and `SetTestSteps`); add/repair a test and fix any gap found
  (e.g. callers with only-local keys skipped, or the graph not recomputing after
  the step cache updates).

## Feature I — Dashboard filters (folder / component / status)

**Design.** Add a filter bar to the Dashboard header with **Folder**,
**Component**, and **Status** selectors. `GetStatistics` gains optional filters:

```go
func (a *App) GetStatistics(profileID string, folder, component, status string) (testrepo.Statistics, error)
```

`repo.GetStatistics` applies them as a `WHERE` over the `test_case` scan (folder
= `folder_id` top-level match; component = membership in the `components` list;
status = exact), so **every** panel (tiles, by-status/priority/folder/label/
component bars, coverage, run-status, trend) recomputes for the filtered subset.
Empty filter = all (today's behavior). The folder/component/status option lists
come from the existing `ListFolders` / `ListComponents` / `ListStatuses`
bindings. A **Clear** button resets them.

## Feature J — Test Environments field on executions and sub-task executions

**Problem.** Xray Test Executions (including sub-task executions) carry a
multi-value **Test Environments** field. The app does not read, store, filter, or
edit it anywhere (`test_container` has no environments column;
`internal/jira` never references the field).

**Design.**
- **Schema v25:** add `environments TEXT NOT NULL DEFAULT ''` to `test_container`
  (a JSON array of environment names). Additive migration with the
  duplicate-column guard; bump `schemaVersion`. A single well-known field as a
  direct column (not the generic custom-field table) keeps filtering and bulk
  edit simple.
- **Jira client + sync:** the container fetch reads the Test Environments
  custom field; `syncContainers` stores it on the `test_container` row. Real path
  marked `TODO(xtm)` behind the demo short-circuit; the demo generator assigns a
  small set (e.g. `Staging`, `Prod`, `Chrome`, `Android`) across executions.
- **Repo:** `GetContainerBoard` / the container list returns `environments []string`
  (`TestPlanBoardRow`/container DTO gains the field). `ContainerQuery` gains an
  `environment` filter (membership test over the JSON array). A single execution's
  environments are edited via a new `SetContainerEnvironments(profileID,
  containerKey, envs []string)` that writes one coalesced `pending_change`
  (entity_type `container_env`) plus an `audit_log` row, committed to Jira by the
  engine as a custom-field update on the Test Execution issue.
- **Bulk + labeling:** `BulkEditContainers(profileID, containerKeys, op)` with ops
  `set_env` / `add_env` / `remove_env` (mirrors `BulkEditTests`), each writing a
  pending change per container. The frontend shows environments as **chips/badges**
  on the execution row and detail in `ContainersView.tsx`, adds an environment
  **filter** control to the Containers toolbar, and adds an **Environments** field
  to the container bulk-edit modal.

## Feature K — Execution Type field on Test issues

**Problem.** Xray Tests have a **Test Type** (a.k.a. execution type:
`Manual` / `Automated` / `Generic` / `Cucumber`). The app never stores or shows
it — `test_case` has no such column, the Browse grid has no column for it, and it
is absent from filtering and bulk edit. (In demo it exists only as the unsynced
`customfield_10100` "Test Type".)

**Design.**
- **Schema v25:** add `exec_type TEXT NOT NULL DEFAULT ''` to `test_case`
  (shares the v25 migration with Feature J). Additive; guarded.
- **Sync:** read the Xray Test Type value during the test pull and store it into
  `test_case.exec_type` (it is a custom field, so the sync resolves the configured
  field id and includes it; real path `TODO(xtm)`). The demo generator assigns a
  type per test so the column is populated offline.
- **Repo + grid:** `TestCase` gains `ExecType`; `ListTests` returns it; `Query`
  gains an `execType` filter. The Browse grid (`TestTable.tsx` `ALL_COLUMNS` /
  `ColKey`) gains an **Exec type** column (configurable, persisted like the
  others), and the Browse filter bar gains an exec-type selector.
- **Bulk + detail:** `BulkEditTests` accepts field `exec_type` (op `set`); the
  bulk-edit modal (`BulkEditModal.tsx` `FIELDS`) gains **Execution type** with a
  fixed option list. `TestDetail.tsx` shows and edits exec type (writing a normal
  field `pending_change`, committed to Jira as the Test Type custom-field update).

## Feature L — Swap preconditions and requirements (single + bulk)

**Problem.** Today you can only add or remove preconditions/requirements one at a
time (single test) or add/remove a single one across many tests
(`BulkAssociatePreconditions` / `BulkAssociateRequirements`, ADD or REMOVE only).
There is no "replace this set with that set" in one step.

**Design.** "Swap" = remove the selected existing items and add the new ones in a
single apply. The replace semantics already exist (`SetTestPreconditions` /
`SetTestRequirements` write the whole set as one `precondition_set` /
`requirement_set` pending change), so:
- **Single test (`TestDetail.tsx`):** add a **Swap** action that opens a picker
  listing current items as checkboxes (tick = remove) plus a multi-pick add list;
  on confirm it computes `new = (current − removed) + added` and calls the
  existing `SetTestPreconditions` / `SetTestRequirements` once. No backend change.
- **Bulk:** new `BulkReplacePreconditions(profileID, testKeys, toRemove, toAdd
  []string)` and `BulkReplaceRequirements(…)` in `testrepo` + `app.go`. Per test:
  `new = (current − toRemove) + toAdd`, then `SetTest…` for that test; returns the
  standard `BulkEditResult` (succeeded/failed). The bulk modals
  (`BulkPreconditionsModal.tsx` / `BulkRequirementsModal.tsx`) gain a **Replace**
  mode alongside Associate/Disassociate, with two pickers (remove-set + add-set).
  Discard/revert already work because the change is recorded as a full-set
  snapshot.

## Out of scope (YAGNI)

- Two-way review/sync of cross-project member *edits* (we only read their basics
  and their bug links).
- Charting the Sankey inside the XLSX itself (we export the edge list, not an
  embedded chart).
- Bulk create-execution across the whole bug list (only the checked subset).
- A generic per-container custom-field store — Feature J adds Test Environments as
  a single direct column, not the full custom-field framework for executions.

## Rollout

Twelve independent slices, each its own commit/PR, in any order; suggested:
D (CSS) → E → L → F → G → H → I → K → J → C → B → A (A is the largest: schema +
sync + board + bug harvest + traceability). J and K share migration v25, so land
them together or sequence their `schemaVersion` bumps. Then the Jira tickets:
one Improvement per feature, with the cross-project bug + traceability work
(A2/A3) tracked under the existing Feature A ticket. If feature doesn not have Jira issue, 
new Jira issue should be created. set the type according to the nature of the feature.
