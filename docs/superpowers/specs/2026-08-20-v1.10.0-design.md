# Xray Test Manager 1.10.0 — Design Spec

**Date:** 2026-08-20
**Base:** `main` @ `7e47259` (1.9.0 released 2026-08-12)
**Jira:** `RND_P_4TFINT_05-336`, `-324`, `-335` (fixVersion `Xray-Test-Management V1.10.0`, id `111452`)
**Status:** approved (design); pending spec review

## Goal

Three independent items, one bug and two improvements:

1. **-336 (Bug)** Preconditions are missing after the first sync on a new profile. The stage is all-or-nothing, very slow, and its failure is swallowed.
2. **-324 (Improvement)** Add a select-all checklist when adding tests to a container, so a folder's tests do not have to be ticked one at a time.
3. **-335 (Improvement)** An in-app product tour for onboarding, re-triggerable from the Tools menu.

The three touch disjoint code. They can land as separate PRs in any order, but -336 goes first because it is the defect and it carries the schema migration.

## Scope decisions

- **-335 covers the core loop only.** One linear tour of roughly eight steps (profile, sync, browse, edit, commit). Per-view tours were considered and deferred: six times the step authoring and six times the maintenance whenever a view's layout moves. The step registry is data-driven so per-view tours can be added later without rework.
- **-335 uses `driver.js`.** This is the project's first new frontend dependency since inception (`package.json` currently holds react, react-dom, react-markdown, remark-gfm). Justified: about 5KB gzipped, MIT, no framework coupling, and it handles spotlight cut-out, popover placement, keyboard navigation, and scroll-into-view. Building in-house was the runner-up and would keep the dependency count at four, at the cost of owning viewport clamping, resize, and late-mounting elements.
- **-336 does not fix the intermittent 401s.** Bounded retry plus a dropped-link count is mitigation. The token that fails mid-run works moments before and after, so the cause is server-side and needs its own investigation against the live instance.
- **-324 needs no backend work.** `ListMatchingKeys` already exists and is already bound (`app.go:3678`).

## 1 · `-336` Precondition sync

### Current state

`internal/syncer/engine.go` `Sync()` runs stages in order: test pull, folders, **preconditions**, requirements, bugs, containers, custom fields, project field options, then `SetSyncState` stamps the watermark.

The precondition stage (`engine.go:182`) is best-effort:

```go
if err := e.syncPreconditions(ctx, profileID, projectKey, onProgress); err != nil {
    log.Printf("xtm: precondition sync failed (continuing): %v", err)
}
```

`syncPreconditions` (`engine.go:453`) calls `e.backend.ListPreconditions`, which for Xray routes through `internal/backend/xray/adapter.go:254` to `jira.ListPreconditions`. That function loops every precondition, issues one `GET /rest/raven/1.0/api/precondition/{key}/test` per item, and sleeps `throttlePreconditions = 150ms` between each (`internal/jira/preconditions.go:140`). It returns only after the whole loop. A context error mid-loop returns `nil, nil, err`, discarding every association collected so far. The store write happens only after that return, and ends with `ReplaceAllTestPreconditions`, which does `DELETE FROM test_precondition WHERE profile_id = ?` before rewriting.

Links are carried as `map[string][]string` (test key to precondition keys) throughout this path, from the backend interface down to the store method.

Measured from `xtm.log`: `RND_P_4JKTVA_05`, 6028 preconditions, 20:10 to 21:02 on 2026/08/11, about 52 minutes. 6028 × 150ms is 15 minutes of pure sleeping before any request time is counted.

An existing profile hides all of this because the table already holds rows from an earlier successful run.

### 1.1 Mark-and-sweep (schema v49)

**Schema.** Add one column to `test_precondition` (`store.go:101`):

```sql
sync_gen INTEGER NOT NULL DEFAULT 0
```

Mirrored in `baseSchema` and in an idempotent `if current < 49` migration block. Bump `schemaVersion` to 49. Existing rows default to generation 0, which is older than any real generation, so the first post-upgrade sync sweeps them normally.

**Generation value.** The engine picks the generation once per sync pass, as the Unix milliseconds at stage start, and passes it down. Monotonic within a profile, and human-readable in the table when debugging.

**Store API.** `ReplaceAllTestPreconditions` (`testrepo.go:646`) is replaced by two methods on `*testrepo.Repository`, keeping the existing `map[string][]string` link shape:

- `MarkTestPreconditions(profileID string, gen int64, links map[string][]string) error` — upsert, stamping `sync_gen = gen`. Safe to call repeatedly during a pass.
- `SweepTestPreconditions(profileID string, gen int64) (int64, error)` — `DELETE FROM test_precondition WHERE profile_id = ? AND sync_gen < ?`, returning the row count for the sync record.

The existing test `TestReplaceAllTestPreconditionsClearsStaleLinks` (`testrepo_test.go:509`) is rewritten against the new pair rather than deleted, since the behavior it guards (stale links do go away on a clean pass) still holds.

**Invariant.** The sweep runs **only** when the pass completed cleanly. If the pass errors or the context is cancelled, no sweep runs. An interrupted sync therefore leaves stale links behind rather than deleting valid ones. That is the inversion of today's failure mode and the core of the fix.

`UpsertPreconditions` (the precondition rows themselves, not the links) keeps its current upsert semantics and needs no generation column, since a precondition that disappears from Jira is already handled by the existing reconcile path.

### 1.2 Batched persistence

Batching has to cross the backend abstraction, which the first draft of this spec overlooked. `ListPreconditions` is declared on the `backend.Backend` interface (`internal/backend/backend.go:152`) and implemented by both the Xray adapter (`xray/adapter.go:254`) and the Kiwi adapter (`kiwi/adapter.go:733`).

**Approach: an optional streaming interface, not a signature change.** Rather than widening `Backend.ListPreconditions` and forcing Kiwi to grow a parameter it gains nothing from, add a narrow opt-in interface that the engine type-asserts:

```go
// PreconditionStreamer is implemented by backends that can report
// preconditions incrementally, so a long pass can be persisted as it runs
// instead of only at the end.
type PreconditionStreamer interface {
    ListPreconditionsStream(
        ctx context.Context,
        projectKey string,
        onProgress func(done, total int),
        onBatch func(pre []Precondition, links map[string][]string) error,
    ) error
}
```

`syncPreconditions` asserts for it and uses the streaming path when available, falling back to the existing `ListPreconditions` call otherwise. `Backend` is unchanged, Kiwi is untouched, and this matches the capability-gating idiom the backend layer already uses. Widening the interface directly was the runner-up and was rejected on that blast radius.

The Xray adapter implements the streamer by delegating to a new `jira.Client.ListPreconditionsStream`; `jira.ListPreconditions` is reimplemented as a thin wrapper over it that accumulates into slices, so existing callers and `preconditions_test.go` keep working.

The callback fires every `preconditionBatchSize = 200` items and once more for the remainder. A non-nil error from `onBatch` aborts the pass, so a store failure is not silently absorbed.

`syncPreconditions` supplies an `onBatch` that opens a transaction, calls `UpsertPreconditions` and `MarkTestPreconditions` for that batch, and commits. A run cut short at item 4000 of 6028 keeps 4000 preconditions and their links.

**One behavior to preserve.** The current early return `if len(preconditions) == 0 && len(links) == 0 { return nil }` (`engine.go:462`) is what keeps an empty or precondition-less project from wiping the table. Under mark-and-sweep that guard becomes unnecessary for safety, but it must still suppress the sweep when the stage found nothing because no Precondition issue type resolved. See section 1.5.

### 1.3 Concurrency, and deleting the sleep

**Delete `throttlePreconditions` entirely.** `Client.do` already paces every outbound request through a shared token bucket (`rate.NewLimiter(syncReqPerSec=20, syncBurst=10)`, `client.go:210`). The fixed 150ms sleep sits on top of that limiter and is redundant. It is also the single largest cost in the stage.

**Add bounded concurrency.** Introduce `preconditionFetchConcurrency = 8`, mirroring `containerFetchConcurrency = 8` (`containers.go:24`) and reusing the worker pattern at `containers.go:158`: a `sync.WaitGroup`, a buffered channel of work, a `sync.Mutex` around `onProgress` (which is not concurrency safe), and results collected under a mutex before being handed to `onBatch` in order.

Expected effect: 6028 preconditions drop from about 52 minutes to roughly 5, with the shared limiter, not a sleep, setting the ceiling.

**Retry on the association read.** Wrap `listPreconditionTests` in a bounded retry (3 attempts, exponential backoff starting at 500ms) for 401 and for timeout errors. Count preconditions whose links were dropped after exhausting retries and report the count on the sync record. This is mitigation for the intermittent 401, not a fix.

### 1.4 Stage ordering

Move the precondition stage ahead of the folder membership walk in `Sync()`. Order becomes: test pull, **preconditions**, folders, requirements, bugs, containers, custom fields, project field options, watermark.

The test pull must stay first: the comment at `engine.go:171` records an earlier first-sync bug where folders ran before tests existed. Preconditions have the same dependency on tests being present, so they move to second, not first.

### 1.5 Visible failure

Today the stage is best-effort and its error is logged and dropped. Two cases are currently conflated and must be split:

- **Benign skip.** No Precondition issue type resolves on the instance, or the project genuinely has zero preconditions. Log and continue exactly as today. The log line `preconditions: N found (type "Pre-Condition") for PROJECT` stays as the discriminator.
- **Real failure.** The stage started and then errored, or the context was cancelled mid-pass. Record a stage failure on the sync record, surface it in sync history and in the UI, and skip the sweep.

The distinction is drawn at the source, not inferred from an empty result: the stage returns a typed outcome saying whether the precondition issue type resolved, how many items the pass intended to cover, and how many it actually persisted. A pass that covered everything sweeps. A pass that resolved no type skips both the sweep and the failure. A pass that started and stopped short skips the sweep and records the failure.

The sync still finishes, since tests are already stored and a hard abort would waste a completed test pull. But it stops reporting clean. `sync_log` (`store.go:201`, columns `id`, `profile_id`, `started_at`, `finished_at`, `outcome`, `fetched`, `error`) grows a `stage_failures TEXT NOT NULL DEFAULT ''` column holding a JSON array of `{stage, message}`, added in the v49 migration. `outcome` gains a `partial` value distinct from the existing success and failure values. The mechanism is generic so the other best-effort stages can adopt it later, but only preconditions populate it in this release.

### 1.6 Testing

- `MarkTestPreconditions` then `SweepTestPreconditions` removes only older generations, on a fixture with two profiles, asserting cross-profile isolation.
- An interrupted pass (context cancelled after the second batch) leaves the earlier batches present and performs no delete.
- A clean pass replacing a link set removes exactly the links that disappeared.
- Migration test: a v48 database with existing `test_precondition` rows upgrades, the rows land at generation 0, and the first sweep removes them.
- Ordering test asserting preconditions run before folders.
- Stage-failure test asserting a failed precondition stage marks `sync_log` and skips the sweep.
- Fallback test: a fake backend that does **not** implement `PreconditionStreamer` still syncs preconditions correctly through the old path, guarding the Kiwi adapter.
- A no-precondition-type run performs no sweep and records no failure, guarding against a benign instance wiping its own links.
- `jira.ListPreconditions` retained as a wrapper still satisfies the existing `preconditions_test.go` cases unchanged.

## 2 · `-324` Select-all when adding tests

### Current state

`frontend/src/components/AddTestsModal.tsx` renders a `FolderTree` beside a paginated list (`PAGE_SIZE = 50`) with one checkbox per row. Tests already in the container render disabled and pre-checked. There is no way to select more than one at a time.

The same component serves the Preconditions view through its `onAdd` prop, so both paths benefit from one change.

### Design

Frontend only. No new bound method; `ListMatchingKeys(profileId, q)` is already exported (`app.go:3678`) and already used by `TestTable.tsx:502`.

**Page-level select-all.** A header row above the list holds a tri-state checkbox (unchecked, indeterminate, checked) reflecting the selectable rows on the current page. Rows already in the container are excluded from both the count and the toggle, since their checkbox is disabled. Clicking selects all selectable rows on the page, or clears them if all are already selected.

**Select all matching.** When the page is fully selected and `total > PAGE_SIZE`, a text action appears reading `Select all N matching`. It calls `ListMatchingKeys` with the identical query object the list effect uses (search, folderId, and the same fixed sort), then sets the selection to that key set minus `existingKeys`. A busy state and an inline error mirror `TestTable`'s `selectingAll` / `selectAllError` handling.

**No shared abstraction yet.** The logic is copied in shape from `TestTable.tsx:502`, not extracted. Two call sites is not a pattern; extracting now would couple a modal to a table for no gain.

The existing footer already renders `Add ${picked.size} test${...}`, so the count updates for free.

### Testing

No frontend test runner exists in this project. Verification is manual against demo mode: select a folder with more than 50 tests, confirm the page toggle covers exactly the 50 visible rows, confirm `Select all N matching` reaches the full folder count, and confirm already-member tests are never added twice.

## 3 · `-335` In-app tour

### Design

**Dependency.** `npm i driver.js`. Bundled by Vite at build time, so there is no runtime network dependency and demo mode is unaffected.

**Files.** New `frontend/src/tour/`:

- `steps.ts` — the tour as data: an array of `{ id, selector, title, body, placement }`. No React, no imports from components, so steps can be reordered or translated without touching behavior.
- `useTour.ts` — a hook that constructs the driver instance, applies theme-aware styling, runs the tour, and writes the seen marker on completion or skip.
- `tour.css` — overrides for driver.js default styling, using the existing CSS custom properties so light and dark both work.

**Targets.** Steps address `data-tour="<id>"` attributes added to the real elements. CSS classes churn with styling work; a dedicated attribute is an explicit contract that a reader can see is load-bearing.

**Steps (8).**

1. Profile picker — which Jira project and connection this window is showing.
2. Sync — pulling from Jira into the local cache.
3. Search and filter bar — how to narrow 10k tests.
4. A test row — selecting a test opens its detail.
5. Detail panel — editing a field is local, not written to Jira yet.
6. Pending-changes badge — where local edits accumulate.
7. Commit — the single point where changes reach Jira.
8. The More menu — where to restart this tour.

Steps 4 through 7 are the local-first model, which is the part of XTM that surprises new users most and the reason the tour exists.

**Auto-start.** Once, after the **first successful sync**, not on first launch. Starting on an empty grid would spotlight elements with no data behind them, which teaches nothing.

**Persistence.** New `tour_seen_version` key in `internal/settings` alongside `theme` and `show_coverage`. It stores the version of the tour content the user has seen, not a boolean, so a later release that rewrites the tour can re-offer it by bumping a constant. Exposed through the existing `GetSettings` / `SetSettings` pair; the `Settings` struct grows one field and no new bound method is added.

**Restart.** One more item in the existing `More` menu (`App.tsx:1206`): `{ key: "tour", label: "Take the tour" }`, placed above the `Diagnostics` entry.

**Demo mode.** The tour runs normally. Demo mode is how the app is usually exercised, so excluding it would mean the feature is rarely seen.

### Risks

- driver.js ships opinionated default CSS. Overriding it for both themes is real work and is budgeted into the second commit rather than treated as incidental.
- Any step targeting an element outside the Browse view would force the tour to drive navigation between views, with all the timing fragility that implies. Confining this release to the core loop avoids it entirely. This constraint should be documented in `steps.ts` so a later contributor adding a step understands why.

### Testing

Manual against demo mode: first run auto-starts after sync and not before; completing writes the seen version; restarting from the More menu works; skipping mid-tour still writes the marker; both themes render legibly. A Go test covers the settings round-trip for `tour_seen_version`.

## Out of scope

- Per-view tours (deferred, see scope decisions).
- Root-causing the intermittent 401 on `/rest/raven/1.0/api/precondition/{key}/test`.
- Applying the new `stage_failures` mechanism to the other best-effort stages (requirements, bugs, containers). The column is added generically, but only the precondition stage populates it in this release.
- Flipping the `Xray-Test-Management V1.9.0` version row to released in Jira, which needs project admin access.

## Delivery

Three PRs, in this order:

1. `-336` precondition sync (schema v49, four commits: mark-and-sweep, streaming plus batching, concurrency, visible failure).
2. `-324` select-all (one commit).
3. `-335` tour (two commits: mechanism and steps, then theming).

Version stamping and `CHANGELOG.md` finalization happen in a release PR after all three land, per the flow in the release notes.
