## Area A — Bugs panel: scrolling, pagination, layout

Covers feedback **F1** plus tickets **-246**, **-247**, **-248**.

### A1. Bug list scroll + pagination + rows-per-page (F1, partly -246/-248)

Symptoms (F1): the bug master list is not scrollable; the pagination / page-nav
controls are clipped (cut off); the rows-per-page selector does not work; default
should be **5 rows per page**.

Current state (grounded): `frontend/src/components/BugsPanel.tsx` paginates the
list (`pageSize` default **15** via `useViewState(profileId,"bugs","pageSize",15)`,
`Pager` component, `.bugs-md-items` list). CSS `.bugs-md-items { flex:1;
overflow-y:auto; }` and the `.bugs-md` grid (`frontend/src/App.css`).

Approach:
- Change the default `pageSize` to **5** (`useViewState(...,"pageSize",5)`), and
  ensure the rows-per-page options include 5 and that selecting one actually
  re-pages (verify the `Pager` `onPageSize` handler is wired and that `pageSize`
  state drives `paged` slicing — it currently does at lines ~324-326, so confirm
  the control is rendered and bound).
- Fix the layout so the list scrolls and the `Pager` is always visible (not
  clipped): the `.bugs-md-list` column must be a flex column with the list
  (`.bugs-md-items`) taking the remaining height (`flex:1; min-height:0;
  overflow-y:auto`) and the `Pager` pinned below it (`flex:0 0 auto`). Audit the
  grid/column heights so the pager is not pushed out of the viewport.
- This is mostly cross-platform CSS + a default change; verify on Windows, then
  validate the scroll behavior on macOS (-246 is the macOS face of the same
  scroll problem; see A2).

Files: `BugsPanel.tsx`, `App.css`, possibly `Pager.tsx`.

### A2. Scrollbar not showing on the Containers/Bugs tab on macOS (-246)

macOS WKWebView uses overlay scrollbars that stay hidden until interaction, so a
tall list/board can look unscrollable. Approach: style scrollbars for the scroll
containers (`::-webkit-scrollbar`, `::-webkit-scrollbar-thumb`) and/or set
`overflow: auto` with a non-zero `min-height:0` on the flex chain so the content
actually scrolls. Confirm the board/list containers have a bounded height.
Validate on the Mac. Files: `App.css`, `ContainersView.tsx`, `BugsPanel.tsx`.

### A3. Sync button overlaps the bug list on macOS (-248)

Layout/flex bug in the Bugs panel header (`.bugs-md-head` / the Sync button row)
where the button overlaps the list on macOS. Likely a flex-shrink / wrapping
issue. Approach: pin the header row (`flex:0 0 auto`) and ensure the list starts
below it. Mostly CSS; validate on the Mac. Files: `BugsPanel.tsx`, `App.css`.

### A4. "Sync Bugs" not working in the Bugs tab on macOS (-247)

Functional bug: the per-view **Sync** in the Bugs tab does nothing on macOS.
Needs a code dig: trace `syncBugs()` in `BugsPanel.tsx` -> `SyncBugs` binding ->
the backend bug-sync path. Determine whether it is macOS-specific (e.g. an error
swallowed silently, a TLS/cert failure now relevant after -243, or a webview
quirk) or a general regression. Reproduce on the Mac; add error surfacing if it
fails silently. Files: `BugsPanel.tsx`, `app.go` (`SyncBugs`), `internal/syncer`,
`internal/jira/bugs.go`.

## Area B — Test-run feature refinement

Covers feedback **F2** and **F3**. These refine the run-info feature shipped in
the alpha.

### B1. Test run detail not visible in the test (F2)

Feedback: "I don't see test run detail implemented in the test." The Run history
section exists (`TestDetail.tsx`), but it is empty unless `test_run` is populated.
`test_run` is filled by the container sync calling `jira.GetTestRuns`, whose
**live** path is a `NOTE(xtm)` stub (`/rest/raven/2.0/api/testruns?testExecKey=`)
that is not verified against a real Xray instance. So on a live profile the
section is empty.

Approach: implement and verify the live Xray test-run fetch against the actual
Xray Server / DC 8.4.0 instance (the endpoint, response shape, status mapping,
environments, executed-by, defects, dates). Until verified, surface a clear empty
state ("No run data synced") vs an error. Confirm the container sync actually runs
`GetTestRuns` for each execution on a live profile and that `RunsForTest` returns
rows. Files: `internal/jira/testruns.go` (live path + parse), `internal/syncer`,
`TestDetail.tsx` (empty/error state).

> Needs a short verification pass against the live Xray instance (same kind of
> work as the earlier Phase 7 wiring).

### B2. Per-test-run status & result; run timestamps; sortable (F3)

Feedback: a single bug can link a test that has **multiple test runs** with
different results, so the single consolidated "Status / Result" shown in the bug
detail is misleading. Move status & result to **each respective test run**, and
give each run a **created & updated timestamp** so runs are sortable.

Approach:
- **Schema:** add `created_at` and `updated_at` to the `test_run` table (it
  currently has `started_at` / `finished_at` only). New migration (next
  schemaVersion). Populate on upsert; `updated_at` changes when a run's status
  changes.
- **Repo:** `GetTestRunHistory` already returns per-run rows (execution, result,
  env, plan, dates, defects); add the new timestamps to `TestRunEntry` and allow
  sorting by them.
- **Bug detail UI:** in `BugsPanel.tsx`, stop presenting a single consolidated
  Result for the affected test as if it were authoritative; instead make the
  per-run breakdown the source of truth (it already lists each run with its own
  result), and make those run rows **sortable by created/updated**. Reconsider
  whether the top-level affected-test "Result" column should show "latest run" or
  be removed in favor of the breakdown.
- Keep the consolidated worst-wins value only where a single summary is genuinely
  needed (e.g. roll-ups), clearly labeled.

Files: `internal/store/store.go` (migration), `internal/testrepo/testruns.go`
(`TestRunEntry` + sort), `BugsPanel.tsx`, `TestDetail.tsx` (run history sort).

> The data-model change (timestamps) is straightforward; the UI rework of where
> status/result lives benefits from a short design note before building.

## Area C — Import JUnit XML to update execution results (F4)

**New feature — needs a design/brainstorming pass before implementation.**

Goal: let a user update a Test Execution's run results by importing a
**JUnit-compatible XML** test report, matching each `<testcase>` to an Xray test
by **summary** (testcase `name` == test summary).

Design sketch (to be refined):
- **Parse:** Go parser for JUnit XML (`<testsuites>/<testsuite>/<testcase
  name="..." classname="...">` with child `<failure>` / `<error>` / `<skipped>`).
  Map: no failure/error/skipped -> PASS; failure/error -> FAIL; skipped -> TODO
  or ABORTED (decide). Capture time/duration if useful.
- **Match:** testcase `name` -> Xray test by **summary** (case / whitespace
  normalization). Handle ambiguity (multiple tests share a summary) and
  no-match; let the user pick the target **Test Execution** to update.
- **Preview:** a modal showing matched / unmatched / ambiguous rows and the
  result each test would get, before applying.
- **Apply:** set each matched member's run result via the existing
  `SetTestRunStatus` / `BulkSetTestRunStatus`, queued as pending changes and
  committed like any run-result edit. Tests not in the execution are skipped (or
  optionally allocated first).
- **UI:** an "Import results (JUnit XML)" action on the Test Execution (Containers
  view), file picker -> preview -> apply.
- **Demo + tests:** Go unit tests for the parser and the summary matcher; a small
  sample JUnit XML fixture.

Open questions for the design pass: skipped -> which run status; matching by
summary vs a testcase->test-key mapping convention; one execution per import vs
auto-create; how duration/timestamps map to the run's created/updated (ties to
B2).

Files (anticipated): new `internal/testrepo/junitimport.go` (+ test), `app.go`
binding, `frontend/src/components/` import modal, `ContainersView.tsx` action.
